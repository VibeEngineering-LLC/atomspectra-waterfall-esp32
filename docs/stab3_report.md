# #STAB-3: Прогон стабильности прошивки v1.2.18 — 4.6 суток непрерывной записи
## Плата ESP32-S3 + детектор AtomSpectra, водопад с персистом во flash

**Дата:** 2026-08-22 → 2026-08-26
**Прошивка:** `firmware-v1.2.18` (релиз от 2026-08-21, включает #FW-64)
**Статус:** ЗАВЕРШЁН. Потерь сегментов нет, регрессия P-011 не повторилась.

---

## 1. Цель

После релиза v1.2.18 требовалось подтвердить на длительном прогоне два свойства:

1. **Отсутствие тихой потери записи** — регрессия класса P-011 (обнаружена 2026-08-16:
   ~13 ч записи терялись без единого сообщения об ошибке). Счётчики
   `seg_lost`/`seg_evicted`/`seg_dropped`, выведенные в heartbeat задачей #FW-64,
   позволяют это проверить объективно, а не по косвенным признакам.
2. **Устойчивость температурной телеметрии** — непрерывность ряда `t1` за весь прогон
   как условие работоспособности температурной компенсации.

---

## 2. Схема эксперимента

```
[детектор AtomSpectra] --USB--> [плата ESP32-S3, v1.2.18] --WiFi--> [приёмник на ПК]
                                        |
                                   flash: водопад (персист)
```

- Режим записи: непрерывный, `interval_sec = 600` (одна строка водопада = 10 мин).
- Разрешение: `channels = 8192`.
- Кольцевой буфер: `ring_capacity = 256`.
- Сбор на стороне ПК: файл спектрограммы `.aswf` + сопутствующий CSV температур
  (`unix_ts;iso;t1;t2;t3`).

Вмешательств в плату по ходу прогона не производилось: перепрошивки, перезагрузки и
изменения конфигурации отсутствовали.

## 5. Наблюдение, требующее пояснения

В CSV присутствует **один разрыв длительностью 2 ч 35 мин**:
`2026-08-22T18:35:50` → `2026-08-22T21:11:16` (9 325 с при медианном интервале 64 с).

Что установлено:
- Плата в этот момент **не перезагружалась** — непрерывный uptime покрывает весь период
  прогона целиком, включая окно разрыва.
- Счётчики потерь на плате остались нулевыми, то есть **на стороне прошивки данные не
  терялись**.
- Значения `t1` до и после разрыва совпадают (26.0 °C), скачка нет.

Что **не** установлено: конкретная причина паузы. Правдоподобные варианты — временная
остановка приёмника на ПК либо кратковременное отключение детектора от USB; ни один из
них по имеющимся данным не подтверждён. Разрыв относится к стороне сбора, а не к
прошивке, но оставлять его без пояснения в отчёте некорректно.

---

## 6. Выводы

1. **Регрессия класса P-011 не воспроизвелась.** За 4.63 суток непрерывной работы все
   счётчики потерь нулевые, а `total_rows` совпадает с `flash_rows`. Телеметрия #FW-64
   даёт возможность утверждать это по прямому измерению, а не по косвенным признакам.
2. **Прошивка v1.2.18 отработала прогон без единой перезагрузки** при постоянной
   нагрузке записи и загрузке CPU около 52 %.
3. **Температурная телеметрия непрерывна** на всём прогоне, ряд пригоден для работы
   компенсации.

**Ограничение области выводов.** Проверялись стабильность тракта записи и непрерывность
температурной телеметрии. Прямая проверка точности температурной компенсации —
измерение дрейфа центроида линии при изменении температуры по данным спектрограммы —
в рамках этого прогона **не выполнялась**, и утверждать что-либо о её численной
точности по приведённым данным нельзя. Для такой оценки требуется отдельный разбор
`.aswf` по положению пика в зависимости от `t1` (кандидат на #STAB-4).
