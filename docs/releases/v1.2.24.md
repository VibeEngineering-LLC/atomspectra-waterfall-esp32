## Highlights

### Base+device spectrum merge: power-loss recovery no longer loses data (AWF-3)

The analyzer (USB-powered from the board) resets its own histogram and clock on any power
loss. Review of the initial AWF-3 commits (`97b71d0..6426bb8`) plus a live board test found
three defects, all fixed:

- **`-rst` bypassing the base clear.** A `-rst` sent via `/api/command` or the TCP bridge
  (BecqMoni/AtomSpectra "Reset" button) reached the instrument without clearing the gateway's
  base, so the Web UI kept showing the old spectrum after a PC-side reset. Fixed with a single
  choke point (`usb_host_send_text_command()`) plus a small SHPROTO decoder added to the TCP
  bridge for the raw-passthrough path.
- **First commit after a real reset landed 9 counts in the base instead of ~267000.** The old
  code folded the base only when a fresh STAT commit arrived; the histogram merge ran
  unconditionally on every commit regardless. On the very first post-reset commit (no fresh
  STAT yet) the merge overwrote the restored spectrum with a near-empty base before the fold
  ever got a chance to preserve it. Fixed: reset detection now also triggers on the histogram
  COUNT (independent of STAT freshness) and runs strictly before any merge, in one function
  shared by production code and host tests.
- **Silent `uint32` overflow** in the base+device merge (bins and total counts accumulate
  across the device's whole lifetime, many power cycles). Now a saturating add.
- **A count-growth reset right before the next fresh time packet could double the count** (review
  round 3 finding, R1). If the first histogram commit after a real reset arrives with the count
  already past the old total but no fresh time packet yet, neither the count check (drop-only) nor
  the time check (needs the packet) can see it; the next commit then folded the already-corrupted
  state. Fixed by deferring publication of that one ambiguous commit instead of merging it — the
  next commit sees the original, uncorrupted state.

Live board test (25.09): power cut on base `194973`, ~7 s of acquisition lost (time between the
last autosave and the cut — one sample; autosave runs about every ~60 s, so worst case is up to
~60 s, not typically "a few seconds") — everything before that was recovered into the base. See the new
README section "Spectrum after a power loss" for the user-facing explanation.

### Field AP fallback: new setting, activity-based return, captive-probe fix (AWF-2a)

Live board tests found the board could get stuck in the field access point (`AtomSpectra-Outdoor`)
for 10+ minutes after the home router came back, or never return at all with the phone's saved
Wi-Fi network auto-reconnecting to the AP.

- **New setting "Fall back to the field access point when Wi-Fi is lost"** (System → Board
  start → Network, `/api/boot-config`). **Off by default** (operator decision — a missing NVS
  key, including after an upgrade, also means off). Off: during operation the board never
  enters Field AP, it reconnects to the router forever (backoff capped at 60 s). The safety net
  always applies regardless of the setting: if Wi-Fi hasn't come up for 5 minutes since
  power-on/reboot, the board raises Field AP anyway — otherwise it would be unreachable after a
  router or password change. On: the board enters Field AP after 5 minutes without the router,
  same as before this release. Takes effect immediately, no reboot.

  **What "off" and "on" actually mean, with timings:**

  | Situation | Setting OFF (default) | Setting ON |
  |---|---|---|
  | Router drops mid-operation, board already had an IP this boot | Never enters Field AP; keeps retrying the router forever on the backoff schedule below | Enters `AtomSpectra-Outdoor` after 300 s (5 min) without the router |
  | Board boots and never gets an IP at all (bad password, router down) | Safety net still fires: Field AP after 300 s (5 min) — same as ON, so the board is never unreachable after a config mistake | Field AP after 300 s (5 min) |
  | STA reconnect attempt spacing | 1, 2, 5, 10, 30, 60 s, repeating at 60 s | same schedule |
  | How often the board checks whether it can leave Field AP | every 150 s (2.5 min), while in Field AP | same |
  | HTTP quiet window required before a return attempt is even considered | 10 min with no real user request (any open socket, e.g. an idle keep-alive/WebSocket, does **not** by itself block the return — only recent requests do) | same |
  | If a return attempt fails (saved SSID scanned but STA doesn't hold) | next attempt after 150 s, then 300, 600, 1200, 2400, capped at 3600 s (2.5/5/10/20/40/60 min); resets to 150 s on the next successful connect | same |

  The "10 min HTTP quiet" and "150 s check" rows only matter once the board is already in
  Field AP — with the setting OFF and an IP already obtained this boot, the board never gets
  there in the first place except through the 300 s safety net above.
- **Return from Field AP now blocks only on real HTTP activity**, not on a phone merely being
  connected to the AP. A phone with `AtomSpectra-Outdoor` saved reconnects to it automatically
  and used to hold the board hostage for 10+ minutes even while idle. Final model (post-review):
  a single timestamp of the last real user request (set from the same request-classifying
  trampoline that already wraps every handler, on every WebSocket frame too, not just the
  handshake) — quiet after 10 minutes with no such request, independent of whether any socket is
  still open. This replaced an intermediate per-socket "active while any user socket is open"
  design that a second review found had no upper bound at all: a phone that walks out of range
  without sending TCP FIN kept its socket ESTABLISHED, and with it the board, in Field AP
  forever. TCP keepalive (`keep_alive_enable`, idle/interval 5 s ×3 probes) was also turned on as
  a second line of defense that reclaims such dead sockets from the httpd pool sooner than the
  11-of-11 LRU purge would.
- **Captive-portal OS probes (Android `generate_204`/`gen_204`, iOS/macOS
  `hotspot-detect.html`/`library/test/success.html`, Windows `ncsi.txt`/`connecttest.txt`, and
  the board's own lightweight captive-landing page) no longer count as activity.** These are
  sent automatically by the phone/OS without the user touching anything; the first activity fix
  above initially still tripped on them because each one opens a connection. A pure URI
  classifier (host-tested against the literal registered probe list) now excludes them.
- **Unregistered URIs (real 404s)** — e.g. Firefox's captive-portal detector
  (`/success.txt`, `/canonical.html`) — are excluded the same way, via a dedicated 404 error
  handler that does not interfere with the existing `httpd_resp_send_err(..., 404, ...)` calls
  made by regular handlers for legitimate reasons (those remain real activity).

Live board test (25.09): Wi-Fi down 2 min → reconnected without a reboot; Wi-Fi down 8 min with
the phone connected to Field AP and setting on → returned after ~6 min; same outage with the
setting off → never entered Field AP, returned immediately once the router came back.

### Also in this release

- **STA reconnect backoff, 1-60 s.** Retry pauses now step `1, 2, 5, 10, 30, 60` s instead of a
  single fixed interval (`WIFI_RECONNECT_SCHEDULE_S`), and the fallback-to-Field-AP decision uses
  one unified 300 s (5-minute) threshold everywhere it applies, instead of several inconsistent
  windows (`WIFI_RECONNECT_FALLBACK_S`).
- **Atomic autosave and backups; restore from tmp/backup on boot.** Spectrum and base snapshots
  are written tmp-then-rename (`atomic_write_snapshot`), so a power loss mid-write cannot leave a
  half-written file mistaken for a good one. Boot-time restore falls back to `current.bin.tmp` or
  the newest rotated backup when the primary file is missing or corrupt; orphaned `*.bin.tmp`
  files left by a power loss during a write are cleaned up at boot.
- **`fs_formatted` in `/api/status`.** Reports whether the LittleFS partition had to be
  reformatted at this boot (empty/corrupt), so a wiped spectrum after a flash write is
  distinguishable from a genuine device reset.
- **Fixed a frozen `time` in `/api/status` across a device power-cycle (AWF-3).** The reported
  elapsed time now comes from the same base+device accumulation as the spectrum merge, so it
  keeps counting up across an instrument reset instead of jumping back to the device's own
  restarted clock.
- **`-Werror=frame-larger-than=3584`** is now enforced on every `main/*` build (0 warnings) —
  catches an oversized stack frame at compile time instead of live on the board.

## Known limitations (see `KNOWN_ISSUES.md`)

- "Reboot instrument" wiping the accumulated spectrum is now FIXED by the base mechanism above —
  removed from the carry-over list.
- Carried over from 1.2.23: the acquisition watchdog still does not guard TCP-bridge-driven
  acquisition; flashing `firmware.factory.bin` still erases NVS.
- The Field AP activity tracker is a heuristic (10-minute HTTP quiet window keyed on the last
  real request, not on socket state) — a client that genuinely stops polling for 10 minutes (tab
  closed, browser killed, phone locked with no background refresh) will be treated as idle, same
  as intended. It also does not see TCP-bridge traffic as activity (new, AWF-2a).
- Two narrow AWF-3 edge cases remain (new, review round 3, not fixed by design — see
  `KNOWN_ISSUES.md`): a rare one-time double-count if the time packet lags more than a few
  seconds around a reset, and a rare stale-base-on-flash race between two back-to-back base
  saves. Neither loses data permanently.

## Русское резюме (для GitHub-релиза)

**Восстановление спектра после обрыва питания.** Прибор при обрыве питания сбрасывает свою
гистограмму и часы; шлюз теперь надёжно сохраняет накопленное в «базу» и накладывает на неё
свежий счёт прибора. Ревью и живой тест на плате нашли и закрыли три дефекта: `-rst` из
BecqMoni/AtomSpectra по TCP или через `/api/command` теперь тоже чистит базу (как кнопка
«Сброс» в Web UI); первый коммит после реального сброса прибора больше не затирает
восстановленный спектр почти нулём (было — база получала 9 отсчётов вместо ~267 тысяч);
сложение база+прибор стало насыщающим (защита от переполнения на очень долгоживущих платах).
Живой тест: обрыв питания на базе 194973, потеряно ~7 секунд (один замер; автосейв идёт раз
в ~60с, худший случай — до ~60с, а не «обычно единицы секунд») — данные до этого момента
восстановлены полностью.

**Настройка ухода в полевую точку доступа.** Новая настройка «Переходить в полевую точку
доступа при потере Wi-Fi» (Система → Старт платы → Сеть) — **по умолчанию ВЫКЛЮЧЕНА**: плата
переподключается к роутеру бесконечно и не поднимает `AtomSpectra-Outdoor` при коротких сбоях.
Страховка работает всегда: если Wi-Fi не поднялся 5 минут с момента включения питания, точка
доступа всё равно появится — иначе после смены пароля или роутера до платы было бы не
достучаться. Отдельно исправлена гонка возврата: раньше просто подключённый к точке телефон
(например, сохранённая сеть переподключилась сама) блокировал возврат домой на 10+ минут;
теперь блокирует только реальная работа с веб-страницей платы. Заодно закрыт побочный дефект:
автоматические пробы связности ОС (Android/iOS/Windows) и попытки открыть несуществующие
страницы браузером тоже раньше засчитывались как «работа с платой» — теперь нет.

**Про галочку подробно, с таймингами.** Настройка «Переходить в полевую точку доступа при
потере Wi-Fi» (System → Старт платы → Сеть) читается из NVS, отсутствие ключа (в т.ч. после
обновления со старой версии) равнозначно ВЫКЛ. Действует сразу, без перезагрузки платы.

| Ситуация | Галочка ВЫКЛ (по умолчанию) | Галочка ВКЛ |
|---|---|---|
| Роутер пропал во время работы, IP в этой загрузке уже был получен | В `AtomSpectra-Outdoor` не уходит никогда, переподключается к роутеру бесконечно по расписанию ниже | Уходит в `AtomSpectra-Outdoor` через 300 с (5 мин) без роутера |
| Плата включилась и вообще не получила IP (неверный пароль, роутер не поднят) | Страховка всё равно срабатывает: точка доступа через 300 с (5 мин) — как при ВКЛ, иначе после ошибки в настройке до платы было бы не достучаться | Точка доступа через 300 с (5 мин) |
| Паузы между попытками STA-реконнекта | 1, 2, 5, 10, 30, 60 с, дальше повторяется по 60 с | то же расписание |
| Как часто плата проверяет возможность выйти из полевой точки | раз в 150 с (2.5 мин), только пока плата в полевой точке | то же |
| Тишина по HTTP, нужная перед попыткой возврата | 10 минут без реального запроса пользователя (сам факт открытого сокета — например, простаивающий keep-alive/WebSocket — возврат НЕ блокирует, блокирует только недавний запрос) | то же |
| Если попытка возврата не удалась (SSID увиден сканированием, но STA не удержалась) | следующая попытка через 150 с, затем 300, 600, 1200, 2400, потолок 3600 с (2.5/5/10/20/40/60 мин); сбрасывается до 150 с при следующем удачном подключении | то же |

Строки «10 минут тишины» и «проверка раз в 150 с» имеют смысл только когда плата уже в
полевой точке — при ВЫКЛ и уже полученном в этой загрузке IP плата туда не попадает вовсе,
кроме как через страховку 300 с выше.

**Проверка перед релизом.** Четыре независимых прохода ревью кода поверх собственных живых
тестов на плате. Первый нашёл переполнение стека при восстановлении (P0) и цикл перезагрузок
Wi-Fi (P1) — оба исправлены. Второй, отдельным проходом, сверил документацию с кодом и

находки уровня P0/P1 — гейт перед релизом пройден. Осталось четыре мелкие находки P2/P3,
задокументированы в `KNOWN_ISSUES.md`, не блокируют выпуск.
