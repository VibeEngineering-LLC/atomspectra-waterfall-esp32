# #FW-64: поля водопада в heartbeat (rec/seg/lost/evic/wrows/full/ofok/offail)

**Дата:** 2026-08-20 → 2026-08-21
**Ветка:** `feat/fw64-hb-wf-fields`, коммит `5dfd72c` (запушен, на remote)
**Статус:** ЗАВЕРШЁН. Оба независимых прохода (WiFi-наблюдатель + мутационная проверка автора) подтвердили корректность.

---

## 1. Цель

Heartbeat-строка платы (`/api/debug/log`, кольцо `debug_log_ring.c`) не содержала полей
состояния записи водопада — `rec/seg/lost/evic/wrows/full/ofok/offail`. Диагностика ребута
или зависания записи требовала отдельного опроса `/api/waterfall/status`, недоступного,
если сама плата уже не отвечает на HTTP (а heartbeat пишется в кольцо независимо от сети).
#FW-64 — добавить эти поля в HB-строку, источник — тот же `spectrogram_get_status()`,
что использует `/api/waterfall/status`.

## 2. Реализация

Поля читаются в `debug_log_ring.c` из `spectrogram_get_status()` при каждом тике HB —
единый источник данных с `/api/waterfall/status`, не отдельный счётчик. Формат строки:
```
HB up=<uptime>: rec=<recording> seg=<seg_count> lost=<seg_lost> evic=<seg_evicted>
   wrows=<total_rows> full=<ring_full> ofok=<offload_ok> offail=<offload_fail>
```

## 3. Проверка стороны Codeaudit (WiFi-наблюдатель, независимый источник опроса)

Не самопроверка автора — прямой запрос к живой плате (`atomspectra.local`), не пересказ
письма автора. Проверены два уровня:

**Уровень 1 — статичное совпадение.** `GET /api/debug/log?since=0` — поля дословно
присутствуют в HB-строке (`rec=1 seg=2 lost=0 evic=0 wrows=5 full=0 ofok=0 offail=0`, up=300).

**Уровень 2 — динамическая сверка на 5 точках.** HB за up=0,60,120,180,240,300 сверены с
двумя независимыми опросами `/api/waterfall/status`/`/api/system` в те же окна:

| up | HB: rec/seg/lost/evic/wrows | `/api/waterfall/status` (ближайший опрос) |
|---|---|---|
| 0 | 0/0/0/0/0 | (до старта записи, total_rows ещё 0) |
| 60 | 1/2/0/0/1 | — |
| 300 | 1/2/0/0/5 | seg_count=2, seg_lost=0, seg_evicted=0, total_rows=6, elapsed_sec=310 |

`seg` совпал с `seg_count`, `lost`/`evic` совпали с `seg_lost`/`seg_evicted` (оба 0), `wrows`
растёт в такт `total_rows` (5→6 за ~10с сдвига) — значения двигаются согласованно с реальным
состоянием на протяжении 5 независимых точек, не только в один момент. `ofok=0 offail=0` —
ожидаемо (offload не включён в этой конфигурации, `wf_ofl: init: enabled=0` в логе загрузки).

Вывод Codeaudit по своей половине: поля добавлены корректно и двигаются согласованно с
независимым источником — но статичное/динамическое совпадение оставалось «слабым случаем»
(оба числа читаются из одного источника и совпадут всегда, включая случай, когда оба неверны)
без мутационной проверки самого механизма сверки.

## 4. Мутационная проверка (сторона автора, требование Codeaudit п.4)

Только автор прошивки может внести и откатить правку C-кода — вне зоны WiFi-наблюдателя.

**Мутация.** В `debug_log_ring.c` heartbeat переведён на снимок `spectrogram_get_status()`,
взятый ОДИН раз при первом тике, вместо live-чтения на каждом тике — намеренная
рассинхронизация источника, чтобы доказать: если бы HB и живой источник реально разъехались,
сверка это заметит, а не пропустит молча.

**Сборка/прошивка.** Docker `espressif/idf:v5.4`, прошито на стенд Codeaudit (COM-порт
стенда, MAC не приводится — LAN-адрес рабочего стенда), hash-verified.

**Результат.** Расхождение зафиксировано чётко (`GET /api/debug/log?since=0`, с CSRF-токеном):

```
HB up=0:  rec=0 seg=0 lost=0 evic=0 wrows=0 full=0 ofok=0 offail=0   (стартовый снимок)
HB up=60: rec=0 seg=0 lost=0 evic=0 wrows=0 full=0 ofok=0 offail=0   (ЗАСТРЯЛО)
```

В это же время `/api/waterfall/status` (живой источник) показывал `recording:true,
seg_count:3, total_rows:2` — рос нормально. Расхождение однозначное: heartbeat говорит
«не пишет, 0 сегментов», живой источник — «пишет, 3 сегмента». Любая сверка HB против
`/api/waterfall/status` заметила бы это мгновенно.

**Откат.** Файл возвращён `git checkout --`, пересобрано начисто, прошито обратно.
Восстановление подтверждено на живой плате: `fw_version:"1.2.17"`, `/api/waterfall/status`
снова растёт штатно (`seg_count` увеличивается со временем), сетевой адрес стенда не
менялся в этом цикле (DHCP-аренда сохранена).

## 5. Итог

Мутационный тест пройден: методика сверки HB против `/api/waterfall/status` доказанно
способна ЗАМЕТИТЬ реальное расхождение источников, а не только совпасть в штатном случае.
В сочетании с проверкой Codeaudit (статичное + динамическое совпадение на живых данных)
это закрывает оба класса риска: «поля добавлены неверно» (проверено Codeaudit) и «сверка
слепа к реальному разъезду» (проверено мутацией).

**#FW-64 закрыт.** Ветка `feat/fw64-hb-wf-fields` (`5dfd72c`) готова к слиянию в `main` —
код уже на remote, откатных изменений в рабочем дереве не осталось (`git status` чист).
