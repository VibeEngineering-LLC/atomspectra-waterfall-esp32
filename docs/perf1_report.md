# #PERF-1…3: ICMP RTT до платы под нагрузкой Web UI, до и после `v1.2.2`

## 2 × 9000 пакетов (30.5 мин на прогон), одна плата, одна сессия

**Дата:** 2026-07-26
**Задачи:** #PERF-1 (кэш спектра), #PERF-2 (HEAVY-полоса), #PERF-3 (rAF-коалесинг)
**Прошивки:** `v1.1.2f` (до) → `v1.2.2` (после). `v1.1.2f` — локальная сборка от
релиза `v1.1.2` с уже применённым `#PERF-5`; буквенные суффиксы остались только
в метках этого прогона, в самой ветке версия одна — `v1.2.2`.
**Статус:** ЗАВЕРШЁН. Целевые перцентили улучшились, обнаружен один артефакт (§5).

> Сырые логи прогонов лежат в локальном `.lab/` и **не публикуются**: они содержат
> внутренний IP платы, SSID точки доступа и локальные пути. В этот отчёт и в
> [`perf1_rtt.csv`](perf1_rtt.csv) попадают только числа RTT и метки прогонов.

## 1. Цель

До `v1.2.2` при открытом Web UI (одна или несколько вкладок) плата ощутимо теряла
отзывчивость: p95 ICMP RTT уходил под 90 мс, отдельные ответы — за секунду, при
нулевой потере пакетов. Гипотеза: конкуренция внутри однопоточного httpd —
рендер спектра на каждый запрос каждой вкладки плюс flash-I/O автосейва в тот же
момент, что и тяжёлая выгрузка.

ICMP взят как метрика, независимая от самого HTTP: он меряет, насколько плата в
принципе успевает обслуживать сеть, и не зависит от того, как быстро отвечает
конкретный эндпоинт.

---

## 2. Схема эксперимента

```
[AtomSpectra детектор]
        │  USB (внутри платы)
        ▼
[ESP32-S3 плата]  ── WiFi 2.4 GHz ──►  [Mac, macOS]
        ▲                                 ping -i 0.2 -c 9000
        │                                       │
   HTTP-нагрузка:                                └─ *.ping.txt → perf1_rtt.csv
   браузер с открытым Web UI
   + AtomSpectra на ПК
```

Нагрузка на оба прогона одинаковая и не менялась по ходу: открытый Web UI в
браузере плюс десктопный AtomSpectra, подключённый к плате. Плата, точка доступа,
Mac и расположение — те же самые; прогоны разнесены на 2.5 часа одного вечера.

---

## 3. Методология

```
ping -i 0.2 -c 9000 <board-ip>          # 9000 пакетов × 0.2 с ≈ 30.5 мин
```

Из вывода берутся значения `time=… ms`; перцентили считаются по отсортированной
выборке, jitter — двумя способами:

- `jitter_rfc3550` — сглаженный |D| в стиле RFC 3550;
- `jitter_successive_mad` — среднее |rtt[i] − rtt[i−1]|.

[`perf1_rtt.csv`](perf1_rtt.csv) — то же сырьё, свёрнутое в окна по 10 с
(50 пакетов на окно): `run, window, elapsed_s, n_ok, loss, min, p50, p95, p99,
max, mean`. 180 окон на прогон, 360 строк.

### Что этот тест НЕ меряет

- **Не меряет WiFi power save.** Обе замеряемые сборки несли `WIFI_PS_NONE`:
  `v1.1.2f` — приватная сборка «база + `#PERF-5`», тега в репозитории у неё нет.
  Поэтому дельта ниже относится к воротам и кэшу, а не к modem sleep.
  **Оговорка о воспроизводимости:** `#PERF-5` приходит отдельным изменением, и на
  этой ветке в отдельности modem sleep включён по умолчанию — собрав только её,
  абсолютные числа ниже вы не получите. Сравнимую конфигурацию даёт ветка с
  `#PERF-5` поверх (или их общий merge).
- **Не меряет пропускную способность** выгрузок — только задержку сети.
- **Один прибор, один вечер, одна точка доступа.** Абсолютные значения привязаны
  к этой конкретной радиообстановке; воспроизводимой считаем дельту, не числа.

| Длительность | 1841.2 с | 1831.0 с | — |
| Потери | **0.0%** | **0.0%** | — |
| min | 3.32 мс | 3.39 мс | +0.07 |
| **p50** | 7.73 мс | **5.05 мс** | **−2.68** |

## 5. Артефакт: максимум вырос, но это всплеск первых 10 минут

Единственная метрика, которая ухудшилась, — абсолютный максимум: 1030 → 2155 мс.
Это **один пакет из 9000**, и он не одинок: в прогоне «после» три окна с
максимумами свыше секунды — №23, №24 и №52, то есть 230–520-я секунды прогона.

Если исключить первые 10 минут и сравнивать установившийся режим (окна 61–180,
по 119 окон в каждом прогоне):

| | до (`v1.1.2f`) | после (`v1.2.2`) |
|---|---|---|
| Худший пакет | 1030.2 мс | **155.6 мс** |
| Среднее по p95 окон | 93.0 мс | **56.0 мс** |

То есть на хвосте прогона «после» вообще нет выбросов уровня секунды, а у
прогона «до» худший пакет как раз там и случился. Всплеск в начале прогона
«после» приходится на первые минуты после перепрошивки и переподключения
клиентов — на нашей стороне отличить радиопомеху от эффекта прошивки этим
прогоном нельзя.

**Честная формулировка:** утверждать «максимум стал хуже» по одному пакету
нельзя, но и заявлять улучшение по максимуму мы не будем: на одиночном прогоне в
живой 2.4 GHz-среде эта метрика слишком шумная. Устойчиво воспроизводимы здесь
p50/p95/p99 и jitter.

## 7. Импликации

### #PERF-1…3 — подтверждены на целевых метриках

Задержка сети под нагрузкой Web UI улучшилась по p50/p95/p99 и по jitter при
неизменных нулевых потерях. Это согласуется с механизмом: снапшот-кэш убирает
дублирующийся рендер спектра на каждую вкладку, HEAVY-полоса разводит по времени
flash-I/O и тяжёлые выгрузки, rAF-коалесинг снимает лишние отрисовки на клиенте.

### Чего этот прогон не закрывает

- Нет измерения на нескольких платах и в разной радиообстановке.
- Нет отдельного A/B именно по `#PERF-5` (WiFi PS) — обе прошивки уже с
  `WIFI_PS_NONE`.
- Максимум по одиночному прогону не является показательной метрикой (§5).
