# Пропуски сегментов и серии HTTP 503 при выгрузке водопада: разбор, исправление, статус

**Дата:** 15 августа 2026 · **Проект:** `atomspectra-waterfall-esp32` · **Связанный issue:** `VibeEngineering-LLC/wf-recorder#1`

Документ для коллаборанта. Описывает две независимые причины отказов при выгрузке сегментов водопада, состояние исправлений и текущий ход проверки на железе. Разметка достоверности: **[Ф]** — факт, подтверждённый исходником, командой или замером; **[Г]** — гипотеза, не подтверждённая замером; **[П]** — проверка запланирована, но не выполнена.

## 1. Что наблюдал пользователь

При выгрузке накопленных данных клиентом `wf_pull_client.py` часть сегментов не забиралась: сервер отвечал `HTTP 503 Service Unavailable` сериями подряд, а сегменты, которые клиент не успел забрать, затем стирались кольцом на плате безвозвратно.

Из отчёта клиента: две серии отказов, 16 и 14 сегментов подряд, между ними успешно забранные сегменты. Клиент удаляет сегмент на плате только после успешной записи на диск, поэтому пропущенные при 503 сегменты оставались на флеш и погибали при вытеснении.

| Параметр среды пользователя | Значение |
|---|---|
| Версия прошивки | v1.2.6 |
| Интервал строки водопада | 180 с |
| Размер сегментов | 102 512 Б (4 строки) |
| Обстоятельство отказа | выгрузка накопленного «за полдня» при заполненной флеш |

Интервал был вычислен из размера сегмента до того, как пользователь его назвал, и совпал: `(102512 − 4104 − 32768) / 16410 = 4` строки, а `N(iv) = min(64, ⌊600 / iv⌋ + 1) = 4` даёт диапазон 151…200 с. Пользователь подтвердил 180 с.

## 2. Причина первая: механизм `#FW-8` не запускался при больших интервалах

### Суть

Кольцо освобождает место на флеш заранее, в середине сегмента, чтобы длительное стирание не совпадало по фазе с записью строки и обслуживанием HTTP. Триггер стоял на 32-й строке сегмента.

**[Ф]** Порог физически недостижим при больших интервалах. Сегмент финализируется по возрасту — `WF_SEG_MAX_AGE_SEC = 600` с — раньше, чем накопит 32 строки. Граница работоспособности:

```
interval_sec ≤ WF_SEG_MAX_AGE_SEC / (WF_SEG_PREP_ROW − 1) = 600 / 31 ≈ 19,35 с
```

При штатном дефолте прошивки `WF_INTERVAL_DEFAULT = 5` с механизм работает и срабатывает в каждом сегменте. При интервале пользователя 180 с он не вызывался **ни разу**, и освобождение места происходило синхронно в пути записи строки — то есть ровно в той фазе, от которой `#FW-8` и должен был увести.

### Доказательная база

| Способ | Результат |
|---|---|
| Арифметика | граница 19,35 с; при 180 с сегмент закрывается на 4-й строке |
| Наблюдение платы | все сегменты имели ровно 11 строк при `interval = 60` с, что совпало с расчётом `⌊600/60⌋ + 1` |
| Эксперимент | при снижении интервала до 15 с порог достигается, `seg_dropped` скачком 0 → 5 ровно на 32-й строке; при возврате на 60 с эффект исчезает |
| Версии | константы идентичны в v1.1.2, v1.2.6 и v1.2.7 — обновление прошивки пользователю не помогло бы |

### Исправление

Смержено в `main`, PR `VibeEngineering-LLC/atomspectra-waterfall-esp32#25`, коммиты `4386941` и `b33fe21`.

1. Введена защёлка `s_seg_prep_done`, сбрасываемая во всех шести местах, где сбрасывается счётчик строк сегмента: финализация, открытие, реконсиляция при загрузке, обе аварийные ветки сброса сегмента, полная очистка.
2. Добавлен второй триггер — **по времени**, на половине возраста сегмента. Он не зависит от числа строк, поэтому закрывает случай любого интервала.
3. Строковый триггер ослаблен со строгого равенства `== WF_SEG_PREP_ROW` до `>= WF_SEG_PREP_ROW` под защёлкой. Прежнее строгое сравнение можно было перескочить: путь отложенного `fflush` инкрементирует счётчик и делает ранний `return`, минуя проверку.

Оба триггера читают и пишут защёлку под одним мьютексом `FSLOCK`, поэтому освобождение вызывается ровно один раз за сегмент, каким бы путём это ни произошло первым.

### Важная поправка, внесённая во второй итерации

Первая версия исправления запрашивала резерв по формуле строкового триггера — «остаток текущего сегмента плюс весь следующий», исходя из роста до 64 строк. Но триггер по времени срабатывает именно тогда, когда сегмент **не** дорастает до 64 строк.

**[Ф]** При интервале 170 с в сегменте на момент срабатывания было 2 строки, а резервировалось место под 128 строк — 2,97 МиБ вместо необходимых около 100 КиБ. На заполненной флеш это выселило бы примерно 30 сегментов пользовательского размера за один залп вместо 10 — то есть **усугубило бы** ровно ту потерю данных, против которой делалось исправление.

Исправлено коммитом `b33fe21`: триггер по времени запрашивает столько же, сколько запросила бы синхронная страховка в пути записи. Объём вытеснения не меняется относительно поведения без триггера — сдвигается только момент стирания.

| Проверка на железе, `interval = 170` с | Первая версия | Финальная версия |
|---|---|---|
| Запрошенный резерв | 2,97 МиБ | 1,02 МиБ |
| Удалено сегментов | 4 | **0** |
| Пик времени ответа HTTP | 19 812 мс | **577 мс** |
| Расхождение счётчиков строк | нет | нет |

## 3. Причина вторая: ворота HEAVY-полосы не переживают выдачу крупного сегмента

Обнаружена позже, при прогоне в режиме, приближенном к пользовательскому. **Это независимый дефект, исправления пока нет.**

### Механизм

**[Ф]** Выдача сегмента идёт через сериализующие ворота с ожиданием слота `WF_SEGMENT_GATE_WAIT_MS = 250` мс, при `concurrency = 1`. Замер показал, что выдача крупного сегмента занимает слот на **1,6…1,8 с** — то есть ожидание короче времени удержания в шесть-семь раз. Любой запрос, пришедший в это окно, получает 503.

### Воспроизведение

**[Ф]** Прогон 35 минут при `interval = 180` с, активном TCP-потоке от прибора (33,8 КБ/с) и одновременной записи водопада: 169 ответов 200 и **один 503**. Источник отказа подтверждён встроенным счётчиком прошивки — `/api/system` вернул `http_heavy_rejects: 1`, ровно совпадая с наблюдаемым.

Ключевое отличие от первой причины: в момент отказа `seg_dropped = 0` и `flash_full = false`, то есть **кольцо не работало и стирания не было**. Значит этот 503 порождается не механизмом `#FW-8`.

Контекст отказа:

| Время | Отдано байт | Длительность | Код |
|---|---|---|---|
| 21:34:34 | 693 272 | 1650 мс | 200 |
| 21:34:48 | 693 272 | 1789 мс | 200 |
| 21:35:00 | 266 612 | 698 мс | 200 |
| **21:35:13** | 55 | 328 мс | **503** |
| 21:35:25 | 184 562 | 658 мс | 200 |

**[Г]** Вероятно, именно этот механизм давал пользователю серии по 16 и 14 отказов: клиент гонит запросы плотным циклом, и слот почти всё время занят предыдущей выдачей. Усугубляющий фактор — приоритеты задач: `tcp_tx` моста имеет приоритет 6, веб-сервер 5, запись водопада 2, и все они делят одно ядро.

### Отдельная альтернативная версия

**[Ф]** Сам клиент документирует в заголовке `wf_pull_client.py`, что mDNS-хост `atomspectra.local` используется по умолчанию, поскольку обходит «VPN-прокси, который может отдавать 503 на прямых LAN-адресах». Если пользователь запускал клиент с явным `--host` и IP-адресом, часть его отказов могла приходить от прокси, а не от платы.

В моих прогонах эта версия исключена: обращение шло по прямому адресу через проводной интерфейс, маршрут не проходил через туннель, и отказ подтверждён счётчиком самой платы. За сторону пользователя поручиться нельзя — **[П]** вопрос стоит задать.

### Кандидаты на исправление

Ни один не выбран, все требуют замера.

1. Увеличить `WF_SEGMENT_GATE_WAIT_MS` до величины, покрывающей выдачу крупного сегмента.
2. Отдавать заголовок `Retry-After` с осмысленным значением, чтобы клиент знал, сколько ждать.
3. Повторять запрос на стороне клиента при 503 — предложение автора issue. Закрывает симптом независимо от версии прошивки и полезно само по себе: без повтора пропуск становится необратимым, поскольку кольцо позже стирает незабранный сегмент.

**[Ф]** Во втором прогоне — том самом, что воспроизводит условия пользователя, — счётчик отказов платы `http_heavy_rejects` **не изменился** (остался равным единице, полученной ранее в фазе 1). То есть за всю выгрузку не было ни одного 503.

Задержки при этом наблюдались: время ответа на служебный запрос доходило до 4714 мс во время выдачи крупного сегмента. Сервер тормозил, но не отказывал.

**Промежуточный вывод по второй причине.** Дефект объективно существует — ожидание слота 250 мс короче времени его удержания при выдаче крупного сегмента. Но **реальный клиент его не вызывает**: между запросами он записывает сегмент на диск, и эта пауза даёт слоту освободиться. Отказ воспроизводится только при более плотном опросе, чем делает клиент, — в моём синтетическом прогоне это дало один отказ на 170 запросов.

Из этого следует, что **серии по 16 и 14 отказов подряд у пользователя моими условиями пока не воспроизведены**. Возможные объяснения, ни одно не подтверждено — **[Г]**: более медленный радиоканал, из-за чего выдача сегмента удерживает слот дольше; параллельно работавший второй потребитель; либо отказы VPN-прокси, о которых предупреждает сам клиент. Вопрос требует уточнения у автора issue.

## 6. Проверенные попутно вопросы

**Целостность после перезагрузок.** **[Ф]** Плата пережила четыре перепрошивки за сессию; после них 44 сегмента с непрерывной нумерацией, без пропусков и дубликатов, все завершённые сегменты сходятся по размеру побайтно. Сегмент, открытый в момент перезагрузки, закрывается укороченным, запись продолжается в новый.

> ⚠️ **В этом абзаце стояло неверное утверждение, и оно привело к потере данных.**
> Первая редакция гласила: «Номера сегментов монотонны и переживают перезагрузку, поэтому клиент не спутает старые сегменты с новыми». Это неверно. Номер в **имени** файла восстанавливается сканом каталога (`spectrogram.c:739`), а не из энергонезависимой памяти: пустой каталог плюс любая перезагрузка начинают нумерацию заново, и имена переиспользуются. Монотонен другой счётчик — `seg_seq`, и он лежит **внутри** файла, а не в его имени. На ошибочном утверждении пользователь потерял 264 строки измерений — разбор в разделе 7.

**Выгрузка по TCP.** **[Ф]** Забрать сегменты `.aswf` по TCP невозможно: мост на порту 8234 — прозрачный транспорт потока прибора, он не знает ничего о файловой системе платы. Сегменты отдаются только по HTTP.

**Побочная находка.** **[Ф]** Правило в `.gitattributes` захватывает бинарный файл `demo/data.bin.gz` как текстовый, из-за чего нормализация переводов строк меняет его на 25 байт при чекауте. К описанным причинам отношения не имеет, вынесено отдельно и в PR #25 не включалось.

## 7. Причина третья: переиспользование имён сегментов — тихое уничтожение данных

Обнаружена 2026-08-16, после публикации первой редакции этого разбора. По тяжести превосходит обе предыдущие: данные не задерживались и не терялись частично — они **уничтожались молча, с отчётом об успехе**.

### Что наблюдал пользователь

Проход клиента отчитался `забрано 66 (+0 строк), отложено 0, ошибок 0`, файл-приёмник не вырос ни на байт, все 66 сегментов удалены с платы. Утрачено 264 строки, ≈13,4 ч записи.

### Механизм

Дефект стыка, ни одна сторона в одиночку не неправа.

**Прошивка [Ф]:** номер в имени файла (`s_seg_next`) восстанавливается при старте сканом каталога — `spectrogram.c:739`, `s_seg_next = any ? maxidx + 1 : 0`. Пустой каталог (клиент всё забрал и подтвердил удаление) плюс любая перезагрузка → нумерация с `seg_00000`. Имена переиспользуются.

**Клиент [Ф]:** ключ идемпотентности — пара (имя, размер). При постоянном интервале записи все полные сегменты весят одинаково, поэтому размер как различитель бесполезен. Проверка стояла **до** скачивания тела, значит заголовок не читался и ни один из имеющихся детекторов не был достижим. Подтверждение удаления отправлялось вне обеих ветвей — уходило и тогда, когда не записано ни строки.

**Воспроизведено на железе [Ф]:** сброс нумерации → накоплен `seg_00000.aswf` (1 087 112 Б, 64 строки) → забран реальным клиентом → перезагрузка → накоплен снова `seg_00000.aswf` того же размера → повторный забор тем же файлом-приёмником. Результат: `(уже вшит, только ack) стёрт на плате`, прирост файла **0 Б**.

### Исправление

**Клиент** ([wf-recorder v0.3.0](https://github.com/VibeEngineering-LLC/wf-recorder/releases/tag/v0.3.0)) — ключ идентичности заменён на отпечаток содержимого; тело скачивается всегда; подтверждение удаления уходит только после записи либо совпадения отпечатка. **Это и есть решение.**

**Прошивка** (`firmware-v1.2.9`) — листинг `GET /api/waterfall/segments` дополнительно отдаёт `seg_seq` и `started_at` из заголовка файла, `null` при неудаче чтения.

### Чего исправление прошивки НЕ делает

**[Ф] В сценарии инцидента (полная перепрошивка со стиранием NVS) добавленные поля не различают эпохи вовсе.** Две независимые причины: `s_seg_seq++` выполняется до сборки заголовка (`spectrogram.c:509`), поэтому первый сегмент каждой эпохи получает `1` — совпадает с предыдущей эпохой; запись водопада стартует раньше синхронизации времени (`spectrogram.c:30-33`), поэтому `started_at` первого сегмента бут-эпохи недостоверен, а заголовок задним числом не патчится.

Корректность обеспечивается **исключительно клиентской проверкой отпечатка**. Изменение в прошивке решает смежные случаи (обычный ребут, `clear`) и служит диагностике, но частью решения исходного дефекта не является.

**[Ф] Уточнение границы, найденное замером:** имя переиспользуется не только при полностью пустом каталоге. Достаточно, чтобы **последний** сегмент был пустым: реконсиляция удаляет файлы без единой полной строки (`spectrogram.c:734`) до вычисления максимума, и освободившееся имя достаётся следующему.

### Связка проверена целиком

**[Ф]** Тот же сценарий с обеими исправленными половинами: имена совпали, размеры совпали побайтно — клиент скачал тело, опознал содержимое как новое, записал 64 строки и только затем удалил. Прирост файла 1 050 240 Б.
